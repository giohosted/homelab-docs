    Backup & Restore

    Backup & Restore Runbook Last Updated: 2026-11-06 Status: Docker-based PBS backup and targeted file-level recovery verified; full VM/CT restoration and long-term reliability remain open

    Procedures for restoring Homelab v3 infrastructure following host failure, data loss, corruption, or application-level problems.

    See runbooks/backup-schedule.md for backup schedules, destinations, retention, verification status, and known failures. Overview Homelab v3 uses several complementary backup mechanisms: - Proxmox Backup Server (PBS) for VM and LXC backups. - rsync for Docker Compose stacks and persistent application data. - Plex built-in database backups. - Planned dedicated Plex full-appdata backups. - Planned Synology Active Backup for Business (ABB) for versioned backup storage. These mechanisms provide different recovery capabilities and must not be treated as interchangeable.

    A scheduled backup job does not guarantee that a usable recovery point exists.

    Before performing any restoration: 1. Identify the affected service and failure scope. 2. Determine whether restoration is necessary or whether a smaller repair is appropriate. 3. Verify that the intended backup exists and is accessible. 4. Confirm the backup is suitable for the required recovery. 5. Assess the risk of overwriting existing data or configurations. 6. Plan the restoration and any required service interruption. 7. Perform the approved recovery operation. 8. Verify the restored service and its dependencies. Important: Restoration procedures can overwrite or replace production data. Follow the established one-step-at-a-time workflow and obtain authorization before consequential changes. Step 3 — Validate the Recovery Point Before proceeding: - Confirm the correct VMID or CTID. - Confirm the backup date and time. - Check whether the archive is accessible. - Review any available verification results. - Confirm the required disks and configuration are included. - Check whether relevant application data resides outside the VM backup. - Determine whether the backup predates the failure or corruption. A backup's presence alone does not guarantee its integrity.

    For consequential recovery, prefer an archive that has passed verification and, where practical, has been tested through a safe restoration. Step 4 — Plan the Restore Decide whether the operation is: - Test restoration: Restore to an isolated environment or different VMID. - Production replacement: Restore the original workload after confirming the existing instance will not conflict. Confirm: - Target Proxmox node. - Target storage. - Available capacity. - Intended VMID or CTID. - Networking and VLAN requirements. - Whether the original guest still exists. - Whether the restored guest may start automatically. - Potential application and database implications. Do not enable automatic startup for a test restoration when the restored guest could conflict with an active production service.

    This is especially important for services using static IP addresses, authentication credentials, cluster membership, or externally connected tunnels. Step 5 — Restore After selecting the verified backup: 1. Select Restore. 2. Confirm the target node. 3. Select the target storage. 4. Confirm the VMID or CTID. 5. Review any overwrite warnings. 6. Confirm startup behavior. 7. Start the approved restoration. 8. Monitor the task log until completion. Do not overwrite the existing production guest without an approved recovery plan. Step 6 — Verify After restoring: - Confirm the VM or LXC boots. - Verify networking and storage. - Check application services. - Verify access to required dependencies. - Review relevant service logs. - Confirm user-facing functionality. - Confirm that the restored service does not conflict with another active instance. Record the archive used, recovery actions, and verification results.

    A successful Proxmox restore task alone does not establish application recovery. Troubleshooting PBS Backups Failing with Connection Reset or ESTALE Historical failure of VM-based PBS: The October 30 proxy restart was only a temporary recovery; the same error recurred October 31–November 2. The active PBS Docker path bypasses the former NFS/FUSE datastore mount. The commands below are retained only for investigating or rolling back to the old VM and must not be run inside the new PBS container as if it used NFS.

    Known symptom: PVE tasks show HTTP/2.0 connection failed / connection reset; PBS proxy journal records unable to get shared lock - ESTALE: Stale file handle. The October incident was traced to a long-lived stale .lock descriptor in the PBS proxy, not to a confirmed loss of historical backup data. Read-only first response if the issue recurs 1. Check failures on both Proxmox nodes and record task IDs, timestamps, affected guests, and error strings. 2. Inspect PBS proxy logs around the failure time (use UTC consistently): TZ=UTC journalctl --utc -u proxmox-backup-proxy -u proxmox-backup \ --since "YYYY-MM-DD HH:MM:SS" --until "YYYY-MM-DD HH:MM:SS" \ --no-pager -o short-iso 3. Inspect the current NFS mount and datastore directory: findmnt --kernel -T /mnt/backups/pbs -o TARGET,SOURCE,FSTYPE,OPTIONS ls -la /mnt/backups/pbs 4. Inspect the current proxy PID and its open lock descriptor. Do not assume PID 594 will recur: pid=$(systemctl show -P MainPID proxmox-backup-proxy) echo "PBS proxy PID: $pid" ls -l "/proc/$pid/fd" 2>&1 | grep -E 'backups|.lock|deleted' || true If a relevant descriptor is found, inspect only that descriptor (use its real FD number): readlink "/proc/$pid/fd/FD_NUMBER" stat -L "/proc/$pid/fd/FD_NUMBER" An ESTALE result on the open descriptor while the current pathname works is strong evidence of a stale in-process handle.
